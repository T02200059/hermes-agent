## 推荐顺序

1. **Bug 类整体对照（先）**  
   按 `owner改动清单-todo.md` § Bug（B01–B38），在 **v2 干净官方树**只读核对：官方已修 / 仍存在 / 部分 / 不适用。  
   *产出*：填完每条「验证状态」。不改产品代码。用 `小模型-bug对照提示词.md`。

2. **收窄必保短名单**  
   结合对照结果：官方已修的从重放范围剔除；「仍需自研」的 bug 并入 P0 能力或独立小包。确认 C01–C10 仍为现网必保。

3. **落地真正定制（P0 → P1）**  
   - 基础设施：patch 加载器、归因（C01–C02）  
   - 现网主路径：飞书审批、**自研舰队路由**、LDAP/API media（C04–C07）  
   - damodel / scrub / skill 门 / i18n（C03、C08–C10）  
   - 再 P1（卡片、explainer、guard、OpenViking…）  
   - P2 与「全量标记 / 官方测全绿」不排期

4. **yaml 整合（穿插）**  
   随 C01 与路由/LDAP 重接时做键合并与缩文件；**单独大爆炸改 yaml 不做**。

5. **（可选）再谈 upstream 大同步策略**  
   本 worktree 已是最新 main；定制重放稳定后再决定是否再切 `owner-v*`。

## 理由（短）

- 负担来自清单膨胀 + 神文件 + 测债，不是「owner 目录选错」。减负靠 **必保短名单 + 能力包**，不靠换魔法 patch，也不靠官方 multiplex。  
- 官方 profile 是同用户同进程；node010 要跨 Linux 用户 → **部署与路由实现维持原舰队**；只可能借鉴声明式「谁→哪个 profile」的可读性。  
- 先分清「官方已修的 bug」再重放定制，避免把已进 upstream 的修复再做一遍，也避免在过时债上雕花。
