# 二次开发规范

> 适用于 `hermes-agent` fork 仓库的定制开发工作。
> 最后更新：2026-06-19（增加 v16改动清单.md 引用与维护规则）

---

## 一、仓库结构背景

本仓库 fork 自 [NousResearch/hermes-agent](https://github.com/NousResearch/hermes-agent)，官方以 `main` 分支持续迭代。我们需要定期同步上游更新（sync fork），同时维护一套独立的定制功能。

**核心矛盾**：定制改动越多，sync fork 时的 merge 冲突越严重。

**解法**：从架构和文件组织层面，把"官方代码"和"我们的定制"尽可能分离。

---

## 二、核心原则

### 2.1 最小侵入源码

官方源码只在必要时做最小改动，优先级：

| 优先级 | 方式 | 适用场景 |
|--------|------|----------|
| **P0** | Hook / 插件 | 所有能通过 hook 实现的功能 |
| **P1** | import 编排 + 运行时 patch | 需要在官方流程中插入自定义逻辑，或对官方定义的数据结构（schema、常量等）进行扩展，但要保持官方源码字面定义与上游一致 |
| **P2** | 直接改源码 | 仅作为最后手段，且必须极致最小化（最好只有参数/标记 + 委托）。任何直接改动都必须在 commit 和代码注释中清晰标注，并记录在 owner/docs/ 中 |

**判断标准**：
- 能用 hook 实现，就不要动源码。
- hook 实现不了时，优先用 `import` 把核心逻辑放在 `owner/`，官方文件只做薄薄的代理/调用/委托。
- 对于官方源码中定义的数据结构（tool schema、配置常量、类定义等），**不要直接修改官方文件里的字面定义**。而是在官方模块加载后，从 `owner/` 进行运行时补丁（post-registration patch）。这样官方源码的文字内容与上游保持一致，极大降低 merge 冲突。
- 只有在上述方式都无法满足时，才做最小化的直接源码改动，并用最短的 `[owner]` 标记 + 委托到 owner/ 实现。

### 2.2 owner 目录作为定制功能的家

所有自定义文件的核心存放位置：`owner/`

```
owner/
├── docs/           # 设计文档、规范、inventory
├── hooks/          # 自定义 hook 脚本
├── SOUL.md         # 人设模板（通用版，被运行时加载）
├── scripts/        # 辅助脚本
└── ...             # 按功能继续扩展
```

**规则**：

- 自定义功能文件**只放在 `owner/` 下**，不散落在官方目录结构中
- 官方目录（`agent/`、`gateway/`、`cli/` 等）原则上不新增文件，也不改动官方文件中的核心数据结构字面定义（schema、常量、方法体等）
- 在官方文件中进行的任何定制改动，必须：
  - 保持改动极小（最好只有 import + 1~3 行薄胶水/委托）
  - 在改动处或紧上方添加 `# [owner] ` 标记（格式统一为短描述 + 指向 owner/ 位置）
  - 优先使用运行时 patch 或委托方式，而非直接在源码里写实现
- 如确需在官方目录创建文件（如测试、临时 patch），必须在 commit message 中标注 `[owner]` 前缀

#### 2.2.1 软链接配置文件约定

`owner/config/` 下的部分配置文件通过软链接映射到 `~/.hermes/` 供运行时加载：

| 源文件（git 仓库内） | 软链接（运行时路径） |
|---|---|
| `owner/config/patch.yaml` | `~/.hermes/patch.yaml` |
| `owner/config/patch_feishu_profile.yaml` | `~/.hermes/patch_feishu_profile.yaml` |

**规则**：

- 这些文件是**实际在用的运行时配置**，不是模板。内部包含真实的 app_id、open_id、api_key 等。
- **内部项目，不需要考虑 git 安全**——这些 key 直接提交到仓库即可，不需要做占位符替换。
- 如需对外分享或开源，另建脱敏的 template 文件，不要改动正在使用的配置文件。

### 2.3 高内聚、低耦合、易插拔

每个定制功能应满足：

- **独立性**：一个功能对应 `owner/` 下一个明确的子目录或文件，不依赖其他定制功能的内部状态
- **可移除**：删除一个功能目录后，其余功能和官方代码不受影响
- **可追踪**：每个功能有对应的文档（`owner/docs/` 下），记录设计意图和实现方式
- **官方源码干净度优先**：官方文件应尽量保持与上游一模一样的字面内容。所有定制逻辑（包括对 schema 的扩展）都通过 owner/ 模块在运行时注入。

## 三、文件组织思想

我们借鉴 **monkey patch** 的组织思路——不是在运行时动态替换官方模块，而是在**文件层面**实现类似的分离效果：

- 官方代码保持干净，像"未被 patch 的原始模块"（字面定义与上游一致）
- `owner/` 下的代码是"patch 集合"，按功能独立组织
- 运行时通过 import 机制，把 patch 注入到官方流程中

**推荐的具体实现模式（基于实际经验）：**

- **薄胶水 + 委托**：在官方类里只新增一个极小的 stub 方法（1-5 行），里面只做 `from owner.xxx import real_impl; return await real_impl(self, ...)`。
- **运行时 post-registration patch**（特别推荐用于 schema / 常量）：官方文件只保留上游原始的 SCHEMA / 常量定义。在 `owner/tools/schema_patches.py`（或类似）中，在模块加载后动态修改已注册对象的 schema。这样官方源码的 dict 字面内容完全不变。
- **集中编排模块**：把跨多处的归属、配置、补丁逻辑集中放在 `owner/attribution.py`、`owner/tools/...` 等小模块里，官方代码只调用这些 helper。
- **彻底移除官方文件里的死代码/注释块**：当用早期返回 + owner/ 委托替代原有逻辑时，直接删除被注释掉的“original code (disabled)”大段代码。解释说明留在 owner/docs/ 或 owner/ 实现文件里。
- **复杂交互/缓存的封装示例（审批卡片经验）**：像 diff cards 一样，对飞书审批卡片（CallBackCard、按钮状态、resolved 更新）和关联的 open_id -> 中文名缓存（pre-warm + TTL），创建 owner/feishu/approval.py + sender_name_cache.py（仅名称部分，chat_id 映射推后）。官方 feishu.py 仅保留 _approval_state（correlation 必需的小状态）、薄薄的 send_exec_approval / handler 委托 + pre_warm 调用 + build_xxx(data) + 统一的短 `# [owner] approval: ... (see owner/feishu/...)`。其他平台 adapter 只做参数接受 + 短注释。run.py 里 sender 传递也加短标记。好处：官方文件对这个特性只剩 ~20-30 行薄胶水，sync 时冲突极小；cache 成为可复用组件（profile、menu 等可共用）。

这样做的好处：

1. sync fork 时，官方目录的 merge 几乎无冲突（甚至很多文件 diff 只有几行 import + [owner] 标记）
2. `owner/` 下的改动是纯增量，不会和官方产生交叉修改
3. 每个 patch（功能）可以独立 review、测试、回滚
4. 官方文件保持“可读的 upstream 状态”，便于未来版本对齐和问题排查

## 四、sync fork 工作流

```
upstream/main ──fetch──→ 本地 main ──force push──→ origin/main
                                          ↓
                                      切新分支（如 owner-v16）
                                          ↓
                                      在新分支上叠加定制改动
```

**要点**：

- `main` 分支始终与 `upstream/main` 保持一致，不做任何定制
- 定制工作在 `owner-v*` 分支上进行
- 每次大版本迭代，从新的 main 切新分支，重新审视哪些定制仍需要

## 五、Commit 规范

| 类型 | 前缀 | 说明 |
|------|------|------|
| 功能 | `feat(owner):` | 在 owner/ 下新增功能 |
| 修复 | `fix(owner):` | 修复定制功能的 bug |
| 文档 | `docs(owner):` | 更新 owner/docs/ 下的文档 |
| 源码改动 | `fix(官方模块):` 或 `refactor(owner):` | 对官方源码的必要最小改动（必须在代码里加 `# [owner] ` 标记，并尽量委托给 owner/ 实现） |
| 同步 | `sync:` | sync fork 或对齐上游 |

## 六、改动清单维护规范

所有定制功能必须在 [`v16改动清单.md`](./v16改动清单.md) 中记录，作为 `原有改动清单.md` 的替代文档。该清单按 v16 改造主题组织，只记录功能代码改动。

### 6.1 什么时候更新

| 场景 | 操作 |
|------|------|
| **新增功能** | 在 `v16改动清单.md` 对应主题下新增一条项目，描述背景问题、解决方案、相关 commit |
| **已有功能 bug fix / 小优化** | **不要新增项目**。找到该功能已有的条目，在「相关 commit」后追加新的 commit 号，并补充一句文字说明本次修复/优化解决了什么问题 |
| **功能废弃或推迟** | 在「附录：废弃 / 暂不迁移项」中新增或更新条目，说明决策和原因 |

### 6.2 更新规则

1. **避免重复追加同一功能**
   - 同一个能力（如「飞书审批卡片重构」、「patch.yaml 统一加载器」）只对应一个项目。
   - 后续对该能力的迭代（性能优化、边界修复、review fixes）全部追加到原有项目的「相关 commit」中，不另起新项目。

2. **新增项目的最小粒度**
   - 一个项目对应一个**用户可感知的能力点**或**架构决策点**。
   - 不要为了记录单个 commit 而拆条。如果多个 commit 共同完成一个能力，合并为一条描述。

3. **已有功能追加 commit 的写法**

   ```markdown
   - **相关 commit**：`abc1234`（初始实现）, `def5678`（修复 XX 场景下的 YY 问题）, `ghi9012`（优化 ZZ 性能）
   ```

   或者：

   ```markdown
   - **相关 commit**：`abc1234`, `def5678`, `ghi9012`
   - **补充说明**：`def5678` 修复了 XX 场景下的 YY 问题；`ghi9012` 将 ZZ 响应时间从 5s 降到 200ms。
   ```

4. **不记录纯文档/标记类 commit**
   - `docs(owner):` 更新 inventory、迁移状态标记、`docs(inventory):` 等提交不写入改动清单。
   - 只有产生行为变更的代码提交才需要记录。

5. **同步 upstream 后的复盘**
   - 每次 sync fork 后，检查 `v16改动清单.md` 中的条目是否仍然准确：
     - 上游已覆盖的功能，移动到附录并标注 `[covered-by-upstream]`；
     - 因上游重构导致实现方式变化的功能，更新「解决方案」和「相关 commit」。

## 七、Checklist（开发前自检）

- [ ] 这个功能**能用 hook 实现吗**？如果能，不要动源码
- [ ] 核心逻辑是否全部放在 `owner/` 下？官方文件是否只剩薄薄的 import + 委托/早期返回？
- [ ] 对于 schema、常量、方法体等官方定义，是否采用“官方源码保持原样 + owner/ 运行时 patch”的方式？
- [ ] 官方文件里的改动处是否都加了 `# [owner] ` 短标记（格式统一，指向 owner/ 位置）？
- [ ] 新文件是否放在了 `owner/` 下？
- [ ] 是否在 `owner/docs/` 下补充了设计文档（包括本次采用的具体编排模式）？
- [ ] 如果是新功能，是否在 `v16改动清单.md` 中新增了独立项目？如果是已有功能的 bug fix / 优化，是否只在原有项目下追加了 commit 号与说明？
- [ ] 删除这个功能对应的 owner/ 子目录后，其余功能和官方代码能否正常运行？
- [ ] 这个改动 sync fork 时会不会产生 merge 冲突？官方文件的字面 diff 是否已经最小化？
