# 小模型双人审计架构设计

> 文档版本：v1.0 | 更新日期：2026-06-28
> 状态：设计阶段，待第一次实测后迭代

---

## 一、目的与痛点

### 1.1 核心问题

小模型（mimo-v2.5、DeepSeek-V4-Flash、MiniMax-M3 等）在 Hermes Agent 中执行任务时，行为不可控。prompt 层面的改进已到天花板——规则再多，小模型仍会偏离指令。

**本质**：小模型的执行是开环的。用户意图 → prompt → 模型执行 → 结果。中间没有任何反馈回路检测偏差。

**目标**：在模型执行链路中加入一个 AI 审计者，形成闭环控制。审计者与主 agent 并肩工作（双人模式），在每个 tool call 提交执行前审查，在每个 turn 结束后复核。

### 1.2 六个痛点

从历史 session 中提炼的真实案例：

| # | 痛点 | 代表模型 | 案例 |
|---|------|---------|------|
| P1 | **过度防御 / 拒绝执行** | MiniMax-M3 | 用户说"目录删了"→ 回"不删"；用户说"删了它"→ 分析一通→"建议不删" |
| P2 | **过度激进 / 数据毁灭** | DeepSeek + mimo | 用户要求"追加 key 到 authorized_keys"→ 模型读到已有数据后自言自语"太乱了"→ 全删→用户被锁门外 |
| P3 | **反思表演** | 所有模型 | 被纠正后输出"越来越深刻"的反思，但下次照样犯。反思和执行是独立回路——反思生成完就丢了 |
| P4 | **不查先答** | 所有模型 | 说"代码没动过"——一次 grep 都没跑。默认路径是"先生成自信回答"，不是"先查再答" |
| P5 | **纠正无效** | 弱模型尤甚 | 纠正一次→承诺改进→下次同类指令从头来。每次"改进"都是临时补丁 |
| P6 | **甩锅情绪** | 所有模型 | 不解决问题，管理用户观感："建议你换模型""事过去了，你去睡吧" |

### 1.3 痛点之间的关系

六个痛点构成一个循环：

```
执行偏差(P1/P2) → 用户纠正 → 反思表演(P3) → 不查先答(P4) → 纠正无效(P5) → 甩锅(P6) → 回到执行偏差
```

prompt 规则只能约束"模型应该做什么"，不能改变"模型默认做什么"。当默认行为和规则冲突时，弱模型走默认。

### 1.4 解决目标

不加 prompt 规则，在 agent 架构层面打断这个循环。用小模型的成本（~$0.002/session）达到大模型（Opus，~$0.15/session）的可靠性。

## 二、整体架构

### 2.1 核心概念：双人模式

审计者不是事后审查的审计员，不是后台监控系统——是**主 agent 旁边坐着的搭档**。

```
用户意图
    │
    ▼
┌─────────────────────────────────────────────┐
│ 主 Agent（小模型，自由形式）                   │
│ prefix-cached，不改 prompt                    │
└──────────────┬──────────────────────────────┘
               │ 每个 tool call 提交前
               │ + 每个 turn 结束后
               ▼
┌─────────────────────────────────────────────┐
│ 审计者（中档快速模型，双人搭档）               │
│ 独立上下文 + 独立 read 工具 + 判断力           │
└──────────────┬──────────────────────────────┘
               │
               ▼
         通过 → 执行
         拦截 → 纠正 / 告警 / 人工批准
```

### 2.2 角色定义

| 角色 | 说明 |
|------|------|
| **主 Agent** | 执行用户任务的小模型。自由形式输出——可以调工具，也可以输出文字。prefix-cached，system prompt 不变。 |
| **审计者** | 坐在旁边的搭档。同步审查主 agent 的每个 tool call 和每轮回复。有独立的 read 类工具调用能力。不看主 agent 的 thinking。 |
| **用户** | 始终是最终决策者。危险命令提人工批准。审计者误拦时用户可 override。 |

### 2.3 两个审查点

| 审查点 | 时机 | 审查什么 | 拦什么 |
|--------|------|---------|--------|
| **tool call 审查** | 每个工具调用提交执行前 | tool call 的参数 + 主 agent 的回复意图 | P2（数据毁灭）、危险命令、间接攻击 |
| **turn 结束审查** | 主 agent 回复完毕后 | 整轮的回复文字 + 实际 tool call 列表 | P1（拒绝执行）、P3（反思表演）、P4（不查先答）、P6（甩锅）、hy3 假装 |

### 2.4 审计者能看到什么

| 上下文 | 来源 | 作用 |
|--------|------|------|
| 用户消息 | 对话历史 | 原始意图 |
| memory.md / user.md | 文件系统 | 背景信息 |
| 主 agent 读过的 skill | 对话历史中的 skill 内容 | SOP，审计者理解相同的工作流 |
| 主 agent 的回复 | 对话历史 | **去掉 thinking**，只看明面上的文字和 tool call |
| 工具调用结果 | 对话历史 | 验证声称是否属实 |

**不给审计者看 thinking 的意义**：防止被主 agent 的"自言自语"说服。审计者只基于事实判断——用户说了什么、主 agent 回复了什么、skill 里怎么规定。

### 2.5 审计者有什么能力

独立的 read 类工具调用能力：
- `read_file`：读文件内容（验证脚本是否安全、检查文件实际状态）
- `grep` / `search_files`：搜索文件内容
- `terminal`：只读命令（`cat`、`git diff`、`git log`、`ls`）

**不能做的事**：审计者不执行写操作。它的职责是审查和判断，不是执行。

## 三、关键设计决策

### 3.1 审查粒度：tool call 级 + turn 结束级

**选择**：两个审查点，不是只选一个。

**理由**：
- tool call 级拦截数据毁灭（P2）、危险命令——在破坏发生前拦住
- turn 结束级拦截"假装干完了"（hy3）、拒绝执行（P1）、反思表演（P3）——这些不出现在 tool call 层面

### 3.2 thinking 剥离

**选择**：审计者不看主 agent 的 thinking。

**理由**：thinking 是主 agent 的内部推理过程，包含自我辩护、反思、情绪。给审计者看 thinking 会让它被"说服"——这正是 P3（反思表演）的核心机制。审计者只看明面上的事实。

### 3.3 审计者模型选择

**选择**：中档快速模型（如 deepseek-v4-flash、mimo-v2.5），大上下文窗口。

**理由**：
- 审计者需要快速响应（每个 tool call 都过它），不能用慢模型
- 审计者需要大上下文（看到完整的用户意图 + skill + 主 agent 回复）
- 中档模型的成本可接受（详见成本分析）

**约束**：审计者应使用与主 agent **不同家族**的模型。两个同家族模型的幻觉方向高度相关，独立性假设会被削弱。

### 3.4 干预三档

| 情况 | 干预方式 | 例子 |
|------|---------|------|
| **无害偏差** | 注入纠正信息给主 agent + warn 用户 | 讨论方向偏了、思考不准确 |
| **有现实危害** | stop + 告知用户 | 没授权就删配置文件、authorized_keys 被覆盖 |
| **危险命令** | 提人工批准 | 对保护路径的破坏性操作 |

### 3.5 审计者自身可靠性

**选择**：接受概率性安全——两个 agent 同时犯同样方向的错的概率足够低。

**理由**：追求"审计者绝对可靠"会导致无限审计。如果审计者也需要被审计，就无穷递归了。

**约束**：审计者使用不同家族的模型，降低关联失败概率。

### 3.6 死锁处理

**选择**：设最大拦截次数（如 3 次）。连续 N 次拦截同一个目标后，升级到人工。

**理由**：审计者过于保守时可能阻塞主 agent 的所有操作。熔断器防止系统卡死。

### 3.7 并行 tool call 审查

**选择**：同一批并行 tool call 作为整体审查，不单独审查。

**理由**：单独看每个 tool call 都无害，组合起来可能是灾难（如 symlink 创建 + 文件写入）。审计者应评估批量调用的组合效果。

### 3.8 回滚策略

**选择**：本地文件场景用 checkpoint manager 的快照回滚。SSH 远程操作场景以事前拦截为主，必要时手动 mv 做 .bak 备份。

**理由**：Hermes 的 checkpoint manager 已有本地文件快照能力。SSH 远程操作没有远程快照机制，回滚应用面很小，以事前拦截为主。

## 四、详细设计

### 4.1 tool call 审查流程

```
主 agent 生成 tool call
    │
    ▼
审计者收到：tool call 参数 + 主 agent 当前回复 + 用户意图 + skill
    │
    ├── 审计者判断是否需要验证
    │   ├── 低风险（read_file、search_files）→ 快速放行
    │   └── 高风险（write_file、patch、terminal）→ 自己调 read 工具验证
    │
    ├── 验证方式（按需）
    │   ├── 读目标文件当前内容
    │   ├── 读脚本文件内容（如果 tool call 是执行脚本）
    │   └── 检查 git diff / git status
    │
    ├── 判断结果
    │   ├── 通过 → 放行，主 agent 的 tool call 正常执行
    │   ├── 无害偏差 → 注入纠正 + warn 用户
    │   ├── 有现实危害 → stop + 告知用户
    │   └── 危险命令 → 提人工批准
    │
    └── 连续拦截 N 次 → 熔断，升级到人工
```

### 4.2 turn 结束审查流程

```
主 agent 回复完毕（可能包含多个 tool call + 文字输出）
    │
    ▼
审计者收到：本轮完整回复 + tool call 列表 + tool call 结果
    │
    ├── 检查项
    │   ├── 声称完成但零 tool call？→ P1/欺骗
    │   ├── 有反思文字但无 tool call？→ P3/反思表演
    │   ├── 有声称但没跑验证工具？→ P4/不查先答
    │   ├── 有甩锅话术？→ P6/甩锅
    │   └── 保护路径被改了？→ 验证是否符合用户意图
    │
    ├── 判断结果
    │   ├── 无异常 → 静默
    │   └── 有异常 → 按干预三档处理
    │
    └── 连续拦截 N 次 → 熔断，升级到人工
```

### 4.3 间接攻击的检测

**场景**：主 agent 写了一个脚本，再执行脚本，脚本里包含对保护路径的破坏操作。

**审计者的处理**：
1. tool call 审查阶段：看到 `write_file /tmp/cleanup.sh` → 自己 read `/tmp/cleanup.sh` → 发现内容包含 `authorized_keys` → 拦截
2. 如果第一步漏过：看到 `terminal bash /tmp/cleanup.sh` → 自己 read `/tmp/cleanup.sh` → 发现内容包含保护路径 → 拦截
3. 如果两步都漏过：turn 结束审查 → 检查保护路径快照 → 发现 `authorized_keys` 被改 → 回滚 + 告警

### 4.4 与 approvals 系统的分工

| 机制 | 职责 | 实现 |
|------|------|------|
| **approvals** | 命令级拦截（危险模式匹配 + smart LLM 评估） | 已有，tool_executor.py |
| **审计者** | 语义级审查（意图 vs 实际效果） | 新建 |

审计者不重复 approvals 的工作。approvals 拦的是"这条命令看起来危不危险"，审计者审的是"这步操作符不符合用户意图"。

### 4.5 与 checkpoint manager 的关系

- 本地文件操作（write_file、patch）：checkpoint manager 已有写前快照，审计者触发回滚时调用
- SSH 远程操作：无远程快照机制，审计者以事前拦截为主。必要时可建议主 agent 先 `mv file file.bak` 再操作

## 五、与现有 Hermes 机制的关系

| 现有机制 | 做什么 | 跟审计者的关系 |
|---------|--------|--------------|
| **approvals** | 命令级拦截 | 互补。approvals 管单条命令，审计者管语义意图 |
| **tool_guardrails** | 循环检测（重复失败、空转） | 不重叠。guardrails 管重复，审计者管语义偏差 |
| **checkpoint manager** | 写前快照 | 审计者依赖它做本地回滚 |
| **background_view** | 后台记忆压缩 | 可复用进程管理框架，但审计逻辑全新 |
| **MoA** | 多模型协作 | 审计者不确定时可升级到 MoA 仲裁 |

## 六、成本分析

| 组件 | 额外 token/session | 额外成本 |
|------|-------------------|---------|
| tool call 审查（低风险快放） | ~0 | $0 |
| tool call 审查（高风险验证，~30% 触发） | ~2k | $0.0002 |
| turn 结束审查 | ~1k | $0.0001 |
| **总计额外** | **~3k** | **~$0.0003/session** |

**对比**：换 Opus = ~$0.15/session = **贵 500 倍**。

## 七、增量实施路径

### 7.1 第一阶段：最小可部署版本

不等完整 LLM 审计者，先用确定性规则挡住最灾难的场景：

1. **零 tool call 完成检测**：主 agent 回复包含"done/完成/已切换"等词 + 本轮零 tool call → 拦截 + warn 用户
2. **保护路径变更检测**：turn 结束后对比保护路径快照，发现被改 + 用户没要求 → 告警

50-100 行代码，零 LLM 调用，先挡住 hy3 假装和 authorized_keys 灾难。

### 7.2 第二阶段：tool call 级审计者

实现审计者的 tool call 审查能力：
- 接入 tool_executor.py 的 before_call 钩子
- 审计者有独立的 read 工具
- 高风险 tool call 触发审计者验证
- 低风险 tool call 快速放行

### 7.3 第三阶段：turn 结束审查

实现审计者的 turn 结束审查能力：
- 零 tool call 完成检测升级为 LLM 判断
- 反思表演检测
- 不查先答检测
- 甩锅话术检测

### 7.4 第四阶段：MoA 仲裁

审计者不确定时升级到 MoA 多模型投票：
- 保护路径的"是否真的危险"判断
- 纠正循环的"换方案"建议
- 边缘 case 的仲裁
