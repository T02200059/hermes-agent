## 2. 从哪来

我们 fork 自 NousResearch/hermes-agent，在源仓 `~/.hermes/hermes-agent` 上叠了大量定制。负担主要来自三块：

1. **源 `owner改动清单.md` 过重**（三千行量级流水账），难当执行面，也不适合整份迁进新树。
2. **定制与官方树纠缠**：sync fork 冲突面大；「官方已修的 bug」和「我们仍要带的能力」混在一起，容易重复劳动。
3. **部署约束固定**：node010 等环境要 **Linux 用户 / 容器舰队隔离**（一人一 home + 独立 gateway）。官方后来的 `multiplex_profiles` 是同用户同进程语义，**不能**用来换掉跨 uid 路由。

因此选 **hybrid**：先在干净官方树上分清「官方 bug 还在不在」，对能直接改官方功能代码的条目做 **fork 自用修复**；再按 **必保短名单 + 能力包** 重放定制，而不是把源清单原样搬过来雕花。

操作上：从已 sync 的官方 `main` 切出 worktree / 分支 **`v2`**，定制代码先不带入；用 [`owner改动清单-todo.md`](./owner改动清单-todo.md) 从零勾选。

## 4. Bug 对照怎么做的

### B 段是什么

[`owner改动清单-todo.md`](./owner改动清单-todo.md) 的 **§ Bug（B01–B38）** 是从源清单提炼的对照 todo。

**「仍存在/需自研」≠「owner 改坏了官方」。**  
尺子是：在 **干净官方 v2 树**上，这个问题还在不在。状态枚举：`官方已修` | `仍存在/需自研` | `部分` | `不适用(纯 owner)` 等。

- **官方已修**：定制重放可跳过或只留回归。  
- **仍存在/需自研**：官方缺口还在，要自带修法或并入 C 段。  
- **不适用(纯 owner)**：官方根本没有这块（如 model_picker、LDAP 门、`_owner_import`）——这才是纯自建能力。

### 怎么对照、怎么修官方树

1. 小模型按 [`小模型-bug对照提示词.md`](./小模型-bug对照提示词.md) 在官方树只读搜代码/测例，填 B 段结论。  
2. 人工 / 助手审核：是否判错、是否把纯 owner 标成官方 bug。  
3. 从「仍存在」里再筛 **O 段**：落在官方功能代码、修法不需要 `owner/` 胶水的，作为 **可直接改官方树的自用 fix**（不提上游）。

O 段分流结果（细节见清单 § 纯官方 bug 待办）：

| 类型 | 条目 | 说明 |
|------|------|------|
| 已实施 | **O3–O8** + **B15** + **B17 官方半边** | O3–O8 见上；B15=`_rebuild_http_client`；B17=cleanup→CANCELLED（飞书中断仍待 C 段） |
| 撤回 | **O1** | 路径 token `\n` 实测 no-op（`\s` 已覆盖），不改 |
| 不改有据 | **O2 / O9** | raw-text 平台面、alibaba 共享 key fallback 属官方设计/部署偏好，不单方面改 |

B15/B17 半边落地后 B 段分布约：**官方已修 23 · 部分 5 · 仍存在 2 · 不适用 8**。仍硬挂 B11 / B12（跟 i18n、SIGINT 证据）；B17 飞书半边进 C 段/混合。

## 5. 和定制的关系

Bug 对照与 O 修复是 **清官方树债**；真正现网差异在 **§ 定制（C01–C25）**。

下一步按 [`v2实现顺序.md`](./v2实现顺序.md) 的 **四阶段**（非旧 P0→P1 标题节奏）：① 非渠道/加载器/终端 → ② 飞书核心底座（审批卡·中文名缓存·i18n·卡基建）→ ③ 飞书定制+杂项（含 LDAP/API media）→ ④ **仅 C05** 多 profile 舰队路由。清单 P0/P1/P2 只作优先级参考。yaml 整合穿插在 C01 与 LDAP/路由重接时做，**不做单独大爆炸**。

官方近几波产品能力（Connectors、本地 LLM 一键、Desktop、multiplex 等）对你们的尺子大多无关或不合部署；**不指望 upstream 产品大头替你们扛定制痛点**。渠道侧以飞书/QQ/微信稳定性与现网行为为准。
